# Store Settings Table Research

## 1. Overview

This document proposes the first database shape for global store settings:

```text
store_settings
```

The current `/admin/settings` page is mock-only. It renders static controls for contact information, shipping notes, and payment notes, but there is no real settings persistence, payment behavior, checkout behavior, or store configuration workflow yet.

This task is research only. The examples below are proposals, not implemented migrations, Ecto schemas, contexts, Repo queries, seeds, tests, settings persistence, payment behavior, or checkout behavior.

## 2. Current Admin Settings Findings

Current route:

```text
/admin/settings
```

Route placement:

- `/admin/settings` is inside the existing `:require_authenticated_user` LiveView session and authenticated browser scope because it is an administrator workflow.

Current admin settings page sections:

- `Contact information`
- `Shipping notes`
- `Payment notes`

Current visible fields:

```text
email
phone
shipping_note
payment_note
```

Current mock settings data also contains:

```text
store_name
tagline
```

However, the current settings page does not render a store information section. Previous admin settings work removed the old store information section, so `store_name` and `store_tagline` should not be required in the first database schema.

The settings page has placeholder Cancel and Save buttons. They do not submit, validate, or persist data.

There are no current settings modules under `lib/**/settings*`, no settings migrations, and no settings Repo queries.

## 3. Storefront Usage Requirements

The storefront currently hardcodes:

- site name `Ca Heo DIY` in the header and footer
- footer description
- support labels
- payment badges for bank transfer and COD
- a footer disclaimer that the storefront is mock-only

Potential future settings usage:

- contact phone or email in footer/support areas
- shipping note on cart/checkout
- payment note on checkout
- payment method copy in the footer or checkout

Do not move all hardcoded storefront text into database settings yet. The current app is still a skeleton, and storing every piece of copy would become a small CMS too early.

## 4. Checkout and Payment Display Requirements

The current cart page shows:

- subtotal
- shipping note placeholder
- checkout link

The current checkout page shows:

- customer information fields
- shipping address fields
- order note
- payment method placeholder
- order summary

Schema implications:

- `shipping_note` is useful now because cart and checkout already show shipping explanation placeholders.
- `payment_note` is useful now because checkout already has a payment placeholder.
- `contact_email` and `contact_phone` are useful for support and manual order/payment coordination.
- Bank account and QR payment fields should be deferred until the payment UI actually displays them.

Do not implement payment confirmation, gateway integration, inventory deduction, or checkout submission in this task.

## 5. Schema Design Options

### Option A: single-row table with explicit columns

Shape:

```text
store_settings
- id
- contact_email
- contact_phone
- payment_note
- shipping_note
- inserted_at
- updated_at
```

Benefits:

- simple to read and update
- clear field names and types
- easy changeset validation
- fits the current admin form
- avoids runtime parsing of setting types

Tradeoffs:

- adding a new setting requires a migration
- not flexible for arbitrary admin-defined settings
- needs a single-row strategy

### Option B: key-value settings table

Shape:

```text
store_settings
- id
- key
- value
- value_type
- inserted_at
- updated_at
```

Benefits:

- flexible for adding new settings without migrations
- can support a dynamic settings UI later

Tradeoffs:

- weaker typing
- more validation logic
- harder to query safely
- more error-prone for booleans, integers, and filenames
- unnecessary for the current small fixed settings form

### Recommendation

Use Option A: a single-row `store_settings` table with explicit columns.

The current admin settings UI is fixed and small. A key-value table would add complexity without solving a real current problem.

## 6. Proposed `store_settings` Table

Recommended first fields:

```text
id
singleton_key
contact_email
contact_phone
payment_note
shipping_note
inserted_at
updated_at
```

Recommended first table meaning:

```text
store_settings = one global row of editable store configuration
```

`singleton_key` is a technical boolean used to enforce that only one row can exist.

## 7. Field-by-Field Explanation

### `id`

- Type: primary key
- Required: yes
- Default: generated by database
- Needed now: yes
- Purpose: stable row identity

### `singleton_key`

- Type: boolean
- Required: yes
- Default: `true`
- Needed now: yes
- Purpose: database-level single-row enforcement

Use a unique index on `singleton_key` plus a check constraint that it must be `true`. This prevents inserting more than one settings row.

### `contact_email`

- Type: string
- Required: no
- Default: none
- Needed now: yes
- Purpose: customer support and manual order coordination

Keep optional because the shop owner may choose phone-only contact or add email later.

### `contact_phone`

- Type: string
- Required: no
- Default: none
- Needed now: yes
- Purpose: customer support, delivery coordination, and manual payment support

Store phone numbers as strings, not integers.

### `payment_note`

- Type: text column in migration, `:string` field in Ecto schema
- Required: no
- Default: none
- Needed now: yes
- Purpose: payment instructions displayed during checkout

This can describe manual bank transfer, COD, or "payment will be confirmed by the shop owner" copy. It should not represent payment state.

### `shipping_note`

- Type: text column in migration, `:string` field in Ecto schema
- Required: no
- Default: none
- Needed now: yes
- Purpose: shipping explanation displayed on cart/checkout

This fits the current owner-operated workflow where shipping is confirmed manually.

### `inserted_at`

- Type: UTC datetime timestamp
- Required: yes
- Default: generated by Ecto timestamps
- Needed now: yes
- Purpose: track when the settings row was created

### `updated_at`

- Type: UTC datetime timestamp
- Required: yes
- Default: generated by Ecto timestamps
- Needed now: yes
- Purpose: track when settings were last changed

## 8. Single-Row vs Key-Value Recommendation

Use a single-row table with explicit columns.

Recommended single-row strategy:

```elixir
add :singleton_key, :boolean, null: false, default: true
create unique_index(:store_settings, [:singleton_key])
create constraint(:store_settings, :singleton_key_true, check: "singleton_key = true")
```

The context can expose functions such as:

```text
get_store_settings()
update_store_settings(attrs)
```

The context should create the first row when needed or depend on seed/setup code later. Do not implement that behavior in this task.

Rejected first-version strategy:

```text
key/value settings
```

Key-value settings should be deferred until the app has a dynamic settings UI or many optional settings with changing shape.

## 9. Indexes and Constraints

Recommended constraints:

- `singleton_key` not null, default `true`
- `singleton_key = true`
- only one row through unique index on `singleton_key`

Recommended indexes:

```elixir
create unique_index(:store_settings, [:singleton_key])
```

No index is needed on contact fields or notes because the app will read the single settings row directly.

If money fields are added later, use integer VND and non-negative check constraints.

## 10. Recommended Ecto Schema Shape

Documentation-only example:

```elixir
schema "store_settings" do
  field :singleton_key, :boolean, default: true
  field :contact_email, :string
  field :contact_phone, :string
  field :payment_note, :string
  field :shipping_note, :string

  timestamps(type: :utc_datetime)
end
```

Recommended naming:

```text
Table name: store_settings
Schema module: CaHeoShop.StoreSettings.StoreSetting
Context module: CaHeoShop.StoreSettings
Route usage: /admin/settings
```

Prefer `CaHeoShop.StoreSettings` over `Settings`, `Store`, `Commerce`, or `Admin`:

- `Settings` is too generic.
- `Store` may later include storefront/catalog behavior.
- `Commerce` is too broad.
- `Admin` should not own business persistence.
- `StoreSettings` clearly names this global settings boundary.

## 11. Recommended Migration Shape

Documentation-only example:

```elixir
create table(:store_settings) do
  add :singleton_key, :boolean, null: false, default: true

  add :contact_email, :string
  add :contact_phone, :string
  add :payment_note, :text
  add :shipping_note, :text

  timestamps(type: :utc_datetime)
end

create unique_index(:store_settings, [:singleton_key])
create constraint(:store_settings, :singleton_key_true, check: "singleton_key = true")
```

These samples should be treated as proposals only.

## 12. Optional or Deferred Fields

### `store_name`

Defer. The storefront currently hardcodes `Ca Heo DIY`, and the admin settings page no longer renders a store information section.

### `store_tagline`

Defer. Mock data contains a tagline, but the current admin settings page does not expose it.

### `store_description`

Defer. This would move the app toward CMS-like content management before it is needed.

### `logo_filename`

Defer. No current UI manages a logo upload or filename.

### `contact_address`

Defer. The current settings page does not show address. Add later if footer/contact pages need it.

### `support_note`

Defer. `payment_note` and `shipping_note` cover the current operational notes.

### `bank_account_name`, `bank_account_number`, `bank_name`

Defer. Useful for manual bank transfer, but only add when checkout actually displays bank transfer instructions.

### `qr_payment_image_filename`

Defer. Useful for QR transfer display later, but no current UI supports QR payment image management.

### `default_shipping_fee`

Defer. Shipping is currently a manual note. If added later, store as integer VND with a non-negative constraint.

### `free_shipping_threshold`

Defer. No free-shipping promotion workflow exists.

### `announcement_text`

Defer. No current announcement banner exists.

### `announcement_enabled`

Defer. Only useful with `announcement_text`.

### `maintenance_mode_enabled`

Defer. No current storefront maintenance workflow exists.

### `updated_by_id`

Defer. Admin audit behavior is not designed yet. Add later if settings change history matters.

## 13. Open Questions

- Should `/admin/settings` eventually restore a store identity section for name, tagline, and logo?
- Should manual bank transfer fields be added before real checkout persistence?
- Should payment settings support COD enable/disable flags later?
- Should shipping fee become a real integer amount before order creation is implemented?
- Should store settings be seeded during deployment or lazily created by the context?
- Should changes to store settings be audited once multiple admins exist?

## 14. Final Recommendation

For the first implementation, create a single-row explicit-column table:

```text
store_settings
- singleton_key
- contact_email
- contact_phone
- payment_note
- shipping_note
```

Recommended modules:

```text
Schema:  CaHeoShop.StoreSettings.StoreSetting
Context: CaHeoShop.StoreSettings
```

Recommended migration shape:

```elixir
create table(:store_settings) do
  add :singleton_key, :boolean, null: false, default: true
  add :contact_email, :string
  add :contact_phone, :string
  add :payment_note, :text
  add :shipping_note, :text

  timestamps(type: :utc_datetime)
end

create unique_index(:store_settings, [:singleton_key])
create constraint(:store_settings, :singleton_key_true, check: "singleton_key = true")
```

This matches the current admin settings UI and avoids a key-value settings system before the app needs one.
